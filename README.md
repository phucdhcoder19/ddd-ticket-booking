# Train Ticket Booking

A high-concurrency train ticket booking system for the Vietnamese North–South railway, built around the Lunar New Year rush. Thousands of customers go after the same seats the moment a sale opens.

The backend is a Spring Boot application organised in **DDD layers**. The frontend is a React + Vite single-page app. The project is mainly about the hard parts of flash-sale ticketing: atomic stock deduction, time-limited seat holds, cache stampede protection, and transaction consistency between Redis and MySQL.

## Features

- **Station & trip search**: 15 stations on the Hanoi → Saigon line and 7 train services (SE1, SE3, SE5, SE7, SE9, TN3, SE22).
- **Lazy trip provisioning**: a trip and its seats (~240 per train) are generated the first time someone searches for that date. A distributed lock stops duplicate generation.
- **Seat map per carriage**: soft seats (2-2 layout), 6-berth and 4-berth sleeper compartments.
- **Distance-based pricing**: fare = distance × class rate × berth-level factor × Lunar New Year peak surcharge.
- **Seat holds with expiry**: selected seats are reserved for 10 minutes (configurable). A background job releases expired holds.
- **Passenger details per seat**: one named passenger per held seat, with discounts (student, child, senior) calculated on the server.
- **Hold → order conversion**: an order is created from a hold in a single transaction.
- **Flash-sale "buy by quantity" flow**: Redis Lua stock deduction backed by a MySQL transaction, with compensation on failure.
- **Sale window**: requests are blocked before the sale opens and after it closes, and the UI shows a countdown.
- **Waiting room**: first come, first served queue on Redis. At most `app.queue.capacity` people are inside at once, and `POST /holds` rejects callers without a valid admission token (`X-Queue-Token`).
- **Metrics**: Prometheus metrics with p50/p95/p99 latency histograms and SLO buckets.

```
train-start → train-controller → train-application → train-domain
                                         ↓                 ↑
```

`train-domain` declares repository **interfaces**. `train-infrastructure` implements them with JPA and Redis, so the domain does not depend on any persistence technology.

## Architecture

### Seat booking flow (per seat)

```
Search trips ──► Pick seats ──► POST /holds ──► (enter passengers) ──► POST /orders
                                    │                                      │
                                    ▼                                      ▼
                          1 MySQL transaction:                   1 MySQL transaction:
                          ① INSERT hold                          flip hold status,
                          ② UPDATE seat SET hold_id=?            write order,
                             WHERE status = 0                    assign seats to order
                          ③ claimed < requested → rollback all
                                    │
                                    ▼
                     HoldReleaseJob (every 10s) frees expired holds
```

### Flash-sale flow (by quantity)

```
⓪ Sale-window check           ← reject before touching stock
① Redis Lua: atomic deduct     ← outside the transaction; rejects most traffic early
┌──────── 1 MySQL transaction ────────┐
│ ② deduct MySQL stock                 │
│ ③ create order                       │
└──────────────────────────────────────┘
If ② or ③ fails → MySQL rolls back automatically, code restores Redis stock (compensation)
```

## Key Design Decisions

**No Redis in the per-seat hold path.** Each seat is its own row, so two customers picking different seats never contend. When two customers pick the *same* seat, `UPDATE ... WHERE status = 0` in MySQL decides who gets it. A Redis layer here would only add a second source of truth to keep in sync.

**All-or-nothing holds.** If a group of three asks for three berths and only two can be claimed, the whole hold is rolled back. A partial hold is something nobody wants to buy, and it would still block those seats for 10 minutes.

**Redis Lua for quantity-based stock.** The read-check-decrement runs as one Lua script. Redis is single-threaded, so no other request can run between the `GET` and the `SET`.

**Cache stampede protection.** `TicketDetailCacheService` and `TripProvisionService` both use cache-aside with a Redisson lock and a **double-check** after the lock is acquired. Only one thread loads from MySQL (or generates seats). The others wait and then read the result.

**No distributed lock on the hold-release job.** The job runs on every instance. The `WHERE status = 0` guard in `releaseOne()` means only one instance can release a given hold, and the others update 0 rows.

**Transactions live in dedicated services** (`HoldTransactionService`, `OrderTransactionService`). `@Transactional` only works through the Spring proxy, so a `this.method()` call inside the same class would silently run without a transaction.

**Prices are not stored on seats.** A fare depends on the station pair and the travel date (peak surcharge), so it is computed at query time by `FarePolicy`. The price is fixed once, when the hold is created.

**Thread and connection pool sizing** (`application.yml`):
- Tomcat threads = `Ncpu × Ucpu × (1 + W/C)` ≈ 12 × 0.8 × 5.7 → **50**
- Hikari pool = `(cores × 2) + disks` ≈ 25 → **20**, fixed size (min = max) so the app never opens new connections in the middle of a traffic spike.

## Getting Started

### Prerequisites

- JDK 25
- Maven 3.9+
- Docker (for MySQL and Redis)
- Node.js 20+ (for the frontend)

### 1. Start MySQL and Redis

The app expects **MySQL on port 3316** and **Redis on port 6319**:

```bash
docker run -d --name pre-event-mysql -p 3316:3306 \
  -e MYSQL_ROOT_PASSWORD=root1234 -e MYSQL_DATABASE=train_ticket mysql:8.0

docker run -d --name pre-event-redis -p 6319:6379 redis:7
```

### 2. Build and run the backend

On Windows, the helper script starts the containers if they are stopped, builds all modules, and runs the app:

```powershell
.\run.ps1
```

Or manually:

```bash
mvn install -DskipTests
mvn -pl train-start spring-boot:run
```

The API is served at **http://localhost:9999/api**.

### 3. Seed the database

Hibernate creates the tables on first start, so **run the app once before seeding**:

```bash
docker exec -i pre-event-mysql mysql -uroot -proot1234 train_ticket < sql/seed.sql
docker exec -i pre-event-mysql mysql -uroot -proot1234 train_ticket < sql/seed-trains.sql
```

| Script                       | Purpose                                                                                         |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| `seed.sql`                   | 15 stations + 4 sample tickets (on sale, not yet open, sale ended, inactive). Idempotent; resets stock. |
| `seed-trains.sql`            | 7 trains and their carriage layouts (templates only; trips and seats are generated lazily).    |
| `migrate-hold-to-seat.sql`   | **Only for existing databases** created before holds moved from quantity-based to per-seat.    |

> ⚠️ `seed.sql` resets `stock_available` to `stock_initial`. It is handy for re-running flash-sale tests, but never run it against real data.

### 4. Run the frontend

```bash
cd train-web
npm install
npm run dev        # http://localhost:5180
```

`train-web/.env` controls whether the UI talks to the real backend:

```env
VITE_API_BASE_URL=http://localhost:9999/api
VITE_USE_MOCK=false    # true = in-browser mock server, no backend needed
```

### 5. Smoke test

```powershell
.\test.ps1
```

This script views a ticket, buys 2 tickets, tries to buy more than the stock, sends a request with a missing field, and checks that the stock went down.

## Configuration

Main settings in `train-start/src/main/resources/application.yml`:

| Key                                | Default                | Description                                                   |
| ---------------------------------- | ---------------------- | ------------------------------------------------------------- |
| `server.port`                      | `9999`                 | HTTP port                                                     |
| `spring.datasource.url`            | `localhost:3316`       | Uses `serverTimezone=Asia/Ho_Chi_Minh`. Changing it shifts hold expiry by 7 hours. |
| `spring.data.redis.port`           | `6319`                 | Redis port                                                    |
| `app.hold.duration`                | `10m`                  | How long a hold reserves seats (set `30s` to watch the job run) |
| `app.hold.scan-interval-ms`        | `10000`                | Interval of the expired-hold release job                      |
| `app.hold.release-batch`           | `200`                  | Max holds released per scan (keeps transactions short)        |
| `app.pricing.peak-from` / `peak-to`| `2027-01-25` / `2027-02-05` | Lunar New Year peak period                               |
| `app.pricing.peak-surcharge`       | `1.35`                 | Fare multiplier during the peak period                        |
| `app.web.allowed-origin-pattern`   | `http://localhost:[*]` | CORS origin. Replace with a real domain in production.        |
| `app.demo.fail-after-deduct`       | `false`                | Set `true` to force a failure after the stock deduction, to check that the transaction rolls back |

## API Reference

All business endpoints are under the `/api` prefix. Actuator stays at `/actuator`.

### Catalog

| Method | Path                | Description                                      |
| ------ | ------------------- | ------------------------------------------------ |
| GET    | `/api/stations`     | List stations in route order                     |
| GET    | `/api/sale-window`  | Current or upcoming sale window (`opensAt`, `serverNow`) |

### Trips

| Method | Path                                                         | Description                                |
| ------ | ------------------------------------------------------------ | ------------------------------------------ |
| GET    | `/api/trips?from=HNO&to=SGO&date=2027-01-28`                 | Search trips (generates them lazily if needed) |
| GET    | `/api/trips/{tripId}/carriages?seatClass=BERTH_4&from=HNO&to=SGO` | Seat map with per-seat prices         |

Seat classes: `SOFT_SEAT`, `BERTH_6`, `BERTH_4`.

### Holds

| Method | Path                     | Description                          |
| ------ | ------------------------ | ------------------------------------ |
| POST   | `/api/holds`             | Hold seats                           |
| GET    | `/api/holds/{holdCode}`  | Hold status and seconds remaining    |
| DELETE | `/api/holds/{holdCode}`  | Cancel a hold and release its seats  |
| PUT    | `/api/holds/{holdCode}/passengers` | Set one passenger per held seat (replaces the previous list) |

```json
POST /api/holds
{
  "tripId": 12,
  "seatClass": "BERTH_4",
  "seatIds": ["C7-1", "C7-2"],
  "from": "HNO",
  "to": "DNA"
}
```

```json
PUT /api/holds/HOLD-1A2B3C4D5E6F/passengers
{
  "passengers": [
    { "seatId": "C7-1", "fullName": "Jane Doe", "idNumber": "001203004567", "phone": "0912345678", "discount": "STUDENT" },
    { "seatId": "C7-2", "fullName": "John Doe", "idNumber": "001203004568", "phone": "0912345678", "discount": "NONE" }
  ]
}
```

Each held seat needs exactly one passenger. The server applies discounts (`STUDENT` −10%, `CHILD` −25%, `SENIOR` −15%) and rounds to the nearest 1,000 VND. `POST /orders` returns `422` until passengers are saved. The order total is the sum of the discounted prices.

### Orders

| Method | Path                        | Description                  |
| ------ | --------------------------- | ---------------------------- |
| POST   | `/api/orders`               | Convert a hold into an order |
| GET    | `/api/orders/{orderNumber}` | Get order details            |

```json
POST /api/orders
{ "holdId": "HOLD-1A2B3C4D5E6F", "paymentMethod": "VNPAY" }
```

### Flash-sale tickets (quantity-based)

| Method | Path                      | Description                 |
| ------ | ------------------------- | --------------------------- |
| GET    | `/api/ticket/{ticketId}`  | Ticket detail (cached)      |
| POST   | `/api/ticket/buy`         | Buy tickets by quantity     |

```json
POST /api/ticket/buy
{ "ticketId": 1, "userId": 101, "quantity": 2 }
```

### Waiting room

| Method | Path                  | Description              |
| ------ | --------------------- | ------------------------ |
| POST   | `/api/queue`          | Join the queue           |
| GET    | `/api/queue/{token}`  | Check the queue position (`404` = unknown or expired, join again) |

The queue uses three Redis keys: `queue:seq` (counter), `queue:waiting` (sorted set, score = arrival number), and `queue:admitted` (sorted set, score = admission expiry in ms). A job runs every second and admits people with one Lua script, so several app instances can run it at the same time without admitting more than `capacity`. Once admitted, the frontend sends the token as `X-Queue-Token` on every request. `POST /holds` returns `403` without it. `POST /orders` frees the slot after a successful order.

| Key                              | Default | Description                                   |
| -------------------------------- | ------- | --------------------------------------------- |
| `app.queue.enabled`              | `true`  | `false` admits everyone and turns off the `/holds` check (useful for load tests) |
| `app.queue.capacity`             | `500`   | Max people inside at once. Set `2` and open 3 tabs to watch the third one wait |
| `app.queue.admission-window`     | `15m`   | How long an admitted person has to buy        |
| `app.queue.max-admit-per-tick`   | `50`    | Max people admitted per job run               |

## Observability

All Actuator endpoints are exposed:

- Health (including circuit breakers): `http://localhost:9999/actuator/health`
- Prometheus scrape: `http://localhost:9999/actuator/prometheus`

`http.server.requests` publishes p50/p95/p99 percentiles and SLO buckets at 100ms, 500ms, 1s, and 2s. Every metric is tagged with `application=train-ticket-booking` so it can be filtered in Grafana. Tomcat MBeans are enabled, so `tomcat.threads.config.max` shows whether the thread pool settings were actually applied.

## Known Limitations / Roadmap

- **Waiting room has no heartbeat.** Someone who closes the tab while waiting keeps their place, and when called their slot stays taken until the admission expires (15 minutes). One admission token can also create several holds.
- **Missing endpoints** the frontend already calls: `GET /me/tickets`, `POST /tickets/{id}/refund`.
- **`Idempotency-Key`** is sent by the frontend on `POST /holds` and `POST /orders` but is not enforced by the backend yet.
- **Stock warm-up** is hardcoded to ticket id `1` in `WarmUpStockJob`. It should select the tickets that are about to go on sale.
- **Schema management** uses Hibernate `ddl-auto: update`. A migration tool such as Flyway should replace it before production.
- **Authentication** is not implemented. `userId` is passed in the request body.
